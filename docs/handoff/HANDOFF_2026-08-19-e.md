## 1. A pergunta, e a resposta honesta

Verificação visual: reabri o campo de telefone corrigido no S-064 e testei um valor inválido de
propósito. Achado: a UX ainda apagava o texto digitado em silêncio quando não dava para
normalizar — sem borda vermelha, sem aviso, só sumia. Corrigido.

Auditoria: nenhuma tinha sido feita sobre o conserto do S-065 (o "turno já passado" na mensagem
semanal). Disparei um agente independente, mandado a REFUTAR, com o mesmo protocolo de comparação
cega já usado no S-063 (especificação própria antes de ler o código, depois comparação
propriedade a propriedade, depois tentativas ativas de quebrar o conserto).

## 2. O que a auditoria achou — confirmado ao vivo antes de aceitar

O conserto do "turno já passado" (S-065) funciona. Mas a auditoria achou um **segundo** defeito,
numa parte adjacente do mesmo código:

```python
# scripts/vps/lembrete_individual.py, ANTES do conserto
def selecionar_semanal(alvo, pessoas, blocos):
    fim = somar_dias(domingo_da_semana(alvo), 7)   # o fim REAL, usado para filtrar
    ...
    return inicio, resultado                        # `fim` não sai daqui

def montar_mensagem_semanal(pessoa, inicio_iso, turnos_da_pessoa, titulo):
    fim_iso = somar_dias(inicio_iso, 7)              # RECALCULADO, fórmula diferente
    ...
```

As duas fórmulas para "fim da semana" só coincidem quando `alvo` é domingo. Em qualquer outro dia
— **inclusive segunda-feira, a cadência real de produção depois do S-065** — elas divergem. A
mensagem prometia "De 24/08 a 31/08" no texto, mas o filtro só tinha buscado turnos até 30/08.
Reproduzi ao vivo:

```
turnos selecionados de fato: []  (turno em 31/08, dentro do prometido, nunca foi buscado)
```

Não é um caso extremo — acontece em **toda** mensagem semanal enviada sob o cron atual.

## 3. O conserto

`selecionar_semanal` agora devolve `(inicio, fim, resultado)` — `fim` sai de um único lugar.
`montar_mensagem_semanal` passou a **receber** `fim_iso` como parâmetro, nunca recalculando por
conta própria. `rodar_semanal` repassa o valor. A auditoria também notou que `max(domingo, alvo)`
do conserto do S-065 sempre resolvia para `alvo` (matematicamente, `domingo_da_semana` nunca é
posterior a `alvo`) — simplificado para `inicio = alvo` direto, removendo uma comparação que nunca
desempatava para o outro lado.

## 5. Achado lateral — no próprio instrumento de medição

Ao adicionar os novos casos do autoteste (a reprodução do bug + a prova do conserto), o contador de
casos no fim do arquivo (`total = 26`, escrito à mão) ficou desatualizado — rodei o autoteste e a
saída dizia "26 de 26 casos corretos" enquanto **32** casos realmente rodavam. Os 6 mais novos
passavam em silêncio, sem contar para nada — exatamente a classe de defeito que a regra "número
escrito à mão apodrece" (o portão `fatos:conferir` deste projeto) existe para pegar, só que desta
vez dentro do próprio autoteste, fora do alcance daquele portão (Python não entra no gate).
Corrigido nos DOIS autotestes que tinham esse padrão: `autoteste_lembrete_individual.py` (o
contador agora incrementa dentro de `caso()`) e `autoteste-selar-arvore.mjs` (mesmo padrão, ainda
correto quando achado, mas igualmente frágil — corrigido preventivamente).
