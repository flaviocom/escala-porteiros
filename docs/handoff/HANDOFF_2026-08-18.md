## 2. `DEP0190` no disparador de validações ao vivo

Com a cópia certa, `npm run vivo:no-ar` saiu **100% verde** (5/5 contra o site publicado) — mas
imprimiu um aviso de depreciação do Node.js que não deveria estar ali.

`scripts/rodar-validacoes-ao-vivo.mjs:92` usava `execFileSync('npm', ['run', nome], {shell:
true})`: com `shell:true`, arquivo e argumentos são concatenados numa linha de comando **sem
escapar** — o padrão que o Node está depreciando porque, se `nome` viesse de fora, seria injeção.
Aqui `nome` só vem de `Object.keys(package.json.scripts)` (nunca de entrada externa), então não é
explorável hoje — mas essa garantia vivia **implícita no fluxo de dados**, e o projeto já baniu
esta mesma classe uma vez, em outro arquivo (P2.16).

**Corrigido:** `execSync` com string única (não aciona o aviso, porque não combina array de
argumentos com shell) + `exigirNomeValido()` em `scripts/lib/guarda-nome-vivo.mjs` — fonte única,
importável sem efeito colateral, usada tanto pelo disparador quanto pelo autoteste. Prova de
mordida em `scripts/autoteste-guarda-nome-vivo.mjs`: 6 nomes limpos aprovados, 10 nomes hostis
(`; rm -rf /`, `` `whoami` ``, `$(whoami)`, `&&`, aspas simples e duplas, maiúsculas, string vazia,
prefixo `npm run`) barrados.

## 3. `npm run citacoes` estava VERMELHO — e duas citações "verdes" mentiam

`docs/TABELA_CONFORMIDADE_PROJETOS_IRMAOS.md` (chegou no commit de sincronização do método global,
não desta esteira) compara dois repositórios lado a lado (charmway-erp × escala-porteiros)
**usando os mesmos nomes de arquivo relativo** (`AGENTS.md`, `docs/pre-voo.json`) nas duas colunas.
O portão `portao-citacoes.mjs`, corretamente escopado só a este repositório, resolvia as citações
da coluna charmway-erp contra o arquivo homônimo **daqui** — 5 delas não bateram (arquivo
inexistente ou linha além do fim) e ficaram vermelhas; uma sexta batia por coincidência de número

**Corrigidas as 6**, trocando `` `arquivo:linha` `` por prosa com o repositório nomeado — o próprio
portão sugere essa saída para citação que não é estável.

🔴 **E duas citações LOCAIS, que o portão aprovava por o arquivo e a linha existirem, apontavam
para o texto ERRADO:** a tabela dizia que `AGENTS.md:73-77` era a "Seção MÉTODO" (é o trecho do
portão genérico) e que `AGENTS.md:38` era a URL do site (é uma linha em branco). A seção MÉTODO
real fica em `AGENTS.md:137-141`; a URL, em `AGENTS.md:97`. **O porquê que interessa:** o próprio
portão já declara essa limitação — prova que arquivo e linha existem, nunca que o conteúdo bate —,
e foi exatamente ela que deixou os dois passarem por dez dias sem ninguém notar.

## 4. P5.3 fechado com fonte, não mais "por medir"

A sessão de 08/08 (S-056) rodava num contêiner sem rede e deixou o teto do `blocos.json`
declarado "por medir" — teto sem fonte seria chute. Esta sessão tem rede. Medido: 43.773 bytes /
183 turnos = 239 bytes/turno (228 em 08/08 — a diferença é o campo de esquema do P5.4, nascido
depois); ~220 turnos/ano (medido em DB-046 para 2027–2029) → **~52,6 KB/ano**. Fonte oficial
consultada (`docs.github.com/.../about-large-files-on-github`): GitHub não documenta um teto
específico do endpoint PUT da Contents API — só o teto GERAL de arquivo (aviso 50 MiB, bloqueio
100 MiB), que se aplica porque a Contents API grava por commit normal. Nenhuma fonte com número
mais restritivo foi encontrada — registrado como não encontrado, não chutado. Usando o mais
conservador dos dois (50 MiB): **~997 anos** de folga no ritmo atual. Fechado no `BACKLOG.md`.
